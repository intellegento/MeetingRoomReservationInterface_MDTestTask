## Шаг 1. План

### Цель

Пользователь открывает страницу, видит брони дня из URL (`?date=YYYY-MM-DD`, по умолчанию «сегодня» по Бишкеку) на сетке рабочего дня, переключает дату кнопками или URL и видит все состояния: загрузка, пусто, ошибка с повтором. Прошедшая дата и начавшиеся брони только для чтения с текстовым пояснением (B6, B11, Q4, Q13).

### ID требований

F1, F2, U1, U2, U3 (ошибка загрузки), B6 (UI: прошедшая дата, прошедшее время), B9 (UI: «сегодня» по Бишкеку, T1), B11 (UI: только чтение), A2 (`role="status"`, `role="alert"`, `aria-busy`, `aria-describedby`). A1 — manual (pre-delivery), в этом этапе только вёрстка без фиксированных ширин.

B12 из plan.md (UI) на этом этапе покрыт границей B11 (`10:10` заблокирована, `10:11` нет при сейчас `10:10:00`) — та же функция `isBookingLocked`; ui-проверка B12 для формы — этап 5.

### Решения по устройству (на согласование при ревью)

1. **URL и Next.js.** Экран `DayView` (`src/features/day-view/`) получает `dateParam: string | null` и `onDateChange(date, mode: "push" | "replace")` через props. `src/app/page.tsx` связывает их с `useSearchParams` / `useRouter` (`next/navigation`) внутри `Suspense`. Тесты рендерят `DayView` с обвязкой, которая хранит `dateParam` в `useState` — без мока `next/navigation`. Связка страницы с роутером проверяется вручную в `npm run dev` (ui-тестов на неё нет).
2. **Невалидная дата** (`isValidDate` из domain ложно, включая `?date=`): экран показывает «сегодня» и вызывает `onDateChange(today, "replace")`; `list` с невалидной датой не вызывается. Без `?date` — «сегодня», URL не меняется.
3. **Часы клиента** — `src/features/clock.ts`: `getNow()`, `setNowForTests()`, `resetNowForTests()` — как `src/server/clock.ts`. «Сегодня» = `getRoomNow(getNow(), ROOM_TIMEZONE)` при рендере. Таймера, который обновляет «сейчас» каждую минуту, на этом этапе нет (линия «сейчас» — срезаемый пункт plan.md).
4. **Сетка.** CSS Grid: 18 рядов по 30 минут (`09:00`…`17:30`, из констант domain). Блок брони — элемент сетки на рядах `[rowStart, rowEnd)`, которые он задевает; внутри рядов — отступы сверху и снизу в минутах (`insetTop`, `insetBottom`), переведённые в проценты высоты блока. Так `10:10–10:40` стоит на рядах `10:00` и `10:30` с отступом 10 мин сверху и 20 мин снизу. Чистая функция `getGridPlacement(start, end)` в `src/components/day-view/grid-placement.ts` (импортирует из domain только константы и `parseTime` — разрешено таблицей слоёв). Прошедшее время — затемнённая полоса той же функцией от `09:00` до границы «прошлого» с текстом «Прошедшее время».
5. **Граница прошлого — бизнес-правило (B6), поэтому в domain:** `isPastDate(date, now)` и `getPastUntil(date, now)` в `src/domain/day.ts`. `getPastUntil` — минута, до которой день прошёл, с обрезкой рабочим днём: прошедшая дата → `18:00`, будущая → `09:00`, сегодня → `clamp(now.minutes, 09:00, 18:00)`. Отдельные функции нужны, т. к. «сегодня после 18:00» — не «прошедшая дата» (баннер не показывается), хотя всё время прошло. **Это две новые функции domain сверх перечня команды — нужно одобрение.**
6. **keepPreviousData.** `useDayBookings` получает `placeholderData: keepPreviousData` (изменение хука этапа 3). Пока новая дата грузится, видны прежние брони, `role="status"` «Загрузка…» и `aria-busy="true"` у сетки. Skeleton — только при первой загрузке (данных ещё нет).
7. **Пустая дата**: вместо сетки — «На эту дату броней нет» и «Забронировать» (на прошедшей дате кнопки нет, U2).
8. **Заглушки**: «Новая бронь», «Забронировать» и клик по будущей брони (кнопка «Изменить бронь HH:mm–HH:mm») — без обработчиков логики, до этапов 5–6.
9. **Тексты** (Q17, допущения): «Загрузка…», «На эту дату броней нет», «Забронировать», «Не удалось загрузить брони», «Повторить», «Прошедшая дата, бронирование недоступно», «Новая бронь», «Бронь уже началась — изменить нельзя» (одна формулировка для начавшихся и прошедших — текст допущения B11), «Прошедшее время», «Без названия», кнопки «Назад», «Сегодня», «Вперёд». Дата показывается в `<time dateTime="YYYY-MM-DD">`.
10. **CSS** — обычный `src/app/globals.css` (классы + CSS-переменные для позиции), без CSS-модулей: в Vitest они не обрабатываются.

Сделано: INC-5 помечен «эквивалентная мутация, не дыра» (`incidents.md`). Заметки ниже переносятся в README на этапе README.

1. **`router.push` против `history.pushState` — оставлено `router.push`.** В Next 16 смена `?date=` через `router.push`/`router.replace` делает RSC-запрос к серверу, поэтому на медленной сети смена даты (URL, заголовок дня) ждёт этот запрос, а затем запрос броней. `window.history.pushState` Next синхронизирует с `useSearchParams` без запроса к серверу. Не меняется, потому что: (а) связка через роутер Next одобрена (решение 2 этапа 4) и проверена вручную, включая кнопку «назад» браузера и `replace` невалидной даты; (б) связка страницы с роутером не покрыта ui-тестами — замена механизма без тестов рискованнее выигрыша; (в) в демо API и страница на одном локальном сервере, задержка заметна только при искусственно медленной сети. Возможное улучшение — в README.
2. **`retry: 1` для загрузки списка** (`src/features/app-providers.tsx`; в тестах `retry: false`).
