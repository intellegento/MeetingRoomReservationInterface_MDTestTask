# Stage 0 — трейс

## Понимание задачи

Источник: [docs/tz.md](../tz.md). Требования ниже взяты только из текста ТЗ.

### 1. Суть задачи

Нужно сделать веб-интерфейс для бронирования одной переговорной комнаты в пределах рабочего дня (09:00–18:00). Пользователь выбирает дату, видит брони на эту дату, может создать, изменить или удалить бронь. Бизнес-правила проверяются в двух местах: в UI и на mock-сервере. Сервер может вернуть конфликт `409`, и UI должен обработать его без потери введённых данных. Проверяют прежде всего инженерную аккуратность: валидацию, состояния UI, отделение API от UI, понятный TypeScript, адаптивность и базовую доступность.

### 2. Явные требования

**Функции пользователя**
1. Выбрать дату — «выбрать дату;»
2. Посмотреть брони на дату — «посмотреть существующие бронирования на выбранную дату;»
3. Выбрать время — «выбрать время начала и окончания;»
4. Создать бронь — «создать бронирование;»
5. Отредактировать бронь — «редактировать бронирование;»
6. Удалить бронь — «удалить бронирование.»
7. Формат отображения выбираем сами — «Формат отображения — на ваш выбор: список, таймлайн, сетка слотов или календарь дня.»

**Бизнес-правила**
8. Рабочий день — «Рабочий день: 09:00–18:00.»
9. Время брони внутри рабочего дня — «Время начала и окончания — в пределах рабочего дня.»
10. Начало раньше конца — «start < end.»
11. Длительность не меньше 30 минут — «Минимальная длительность — 30 минут.»
12. Длительность не больше 2 часов — «Максимальная длительность — 2 часа.»
13. Брони не пересекаются — «Бронирования не могут пересекаться.»
14. Касание границ не конфликт — «Касание границ конфликтом не считается: 10:00–11:00 и 11:00–12:00 — допустимо.»
15. Нельзя бронировать прошедшее время — «Нельзя бронировать прошедшее время.»
16. Сегодня прошедшие слоты недоступны — «Для сегодняшней даты прошедшие слоты недоступны.»
17. На прошедшие даты нельзя создавать — «Для прошедших дат создание брони недоступно.»
18. При редактировании бронь не конфликтует сама с собой — «При редактировании текущая бронь не должна конфликтовать сама с собой.»
19. Сервер может вернуть конфликт — «Сервер может вернуть конфликт, даже если UI считал слот свободным.» и «Это ожидаемое поведение, а не баг.»
20. Как обработать конфликт — «показать понятное сообщение, обновить список броней и не потерять данные, введённые пользователем.»

**Стек и архитектура**
21. Фреймворк — «React/ Next.js/Vue.js.»
22. TypeScript — «TypeScript — обязательно.»
23. Стили, state-менеджер и формы выбираем сами — «Стили, state-менеджмент, формы — на ваш выбор.»
24. UI-библиотеки и иконки можно — «UI-библиотеки и иконки использовать можно.»
25. Mock API, если нужен сервер — «Если нужен сервер — реализуйте mock API (MSW, Route Handlers, in-memory store и т.п.).»
26. Сетевой слой отделён от UI и заменяем — «Сетевой слой должен быть отделён от UI и легко заменяем на реальный API.»
27. Примерный контракт — «GET /api/bookings?date=YYYY-MM-DD», «POST /api/bookings», «PATCH /api/bookings/:id», «DELETE /api/bookings/:id»
28. Тип `Booking` — `id: string; date: string; // YYYY-MM-DD; start: string; // HH:mm; end: string; // HH:mm; title?: string;`
29. Сервер проверяет правила и умеет отдавать 409 — «Сервер валидирует бизнес-правила и умеет возвращать конфликт (`409`).»

**Процесс**
30. Таймбокс — «Ориентир: 4–6 часов.»
31. Если не успеваем — «остановитесь и в README опишите, что бы доделали и какие были приоритеты.»

### 3. Неявные требования, которые следуют из ТЗ

- **Правила проверяются дважды.** UI проверяет их, чтобы сразу показать ошибку. Сервер проверяет их сам, потому что «Сервер валидирует бизнес-правила». Логику правил удобно вынести в общий модуль и использовать в обоих местах.
- **Конфликт можно воспроизвести.** Правило 8 нужно показать на деле. Mock-сервер должен уметь вернуть 409, когда UI считал слот свободным: например, другой «клиент» занял слот или данные у UI устарели.
- **Редактирование тоже проверяется.** При PATCH сервер проверяет пересечения со всеми бронями, кроме изменяемой (правило 7), и тоже может вернуть 409.
- **Ошибки бывают не только 409.** «Обработку серверных ошибок, в том числе конфликтов» означает, что нужно обработать и ошибку валидации, и сетевую ошибку, и 404 (например, бронь уже удалили).
- **Форма не сбрасывается при ошибке.** После любой ошибки отправки введённые данные остаются в форме, а не только после 409.
- **«Сейчас» влияет на правила.** Правило 6 зависит от текущего времени. Значит, текущее время нужно передавать в функции валидации как параметр, чтобы их можно было тестировать.
- **Время сравнивается как время.** `start`/`end` хранятся строками `HH:mm`, а даты строками `YYYY-MM-DD`. Сравнивать их нужно в минутах или как даты, а не как произвольные строки.
- **Каждое действие показывает своё состояние.** Загрузка, пустое состояние, ошибка и отправка формы нужны и для списка, и для формы, и для удаления.
- **API можно подменить.** UI обращается к API через интерфейс или клиент, а не через `fetch` прямо в компонентах. Тогда mock-сервер заменяется на реальный без правки UI.
- **Демо должно работать после деплоя.** Нужна ссылка на демо, поэтому mock API должен работать на хостинге: Route Handlers на Vercel или MSW в браузере.

### 6. Что ТЗ прямо называет ненужным

- «Реальный бэкенд, авторизация, БД и интеграции не нужны.»

Отсюда следует: пользователей нет, у броней нет владельца, и любой может изменить или удалить любую бронь. Данные хранятся в памяти и могут пропасть при перезапуске сервера.

### 7. Где я не уверен, как понимать ТЗ

1. **Чьё «сейчас» и в каком часовом поясе.** Правило 6 говорит о «сегодняшней дате» и «прошедших слотах», но не указывает, чьё это время. Это может быть время браузера пользователя или время сервера. После деплоя на Vercel сервер работает в UTC, а пользователь, например, в UTC+6. Из-за этого UI и сервер могут по-разному решить, какой сегодня день и какие слоты уже прошли.
2. **Можно ли менять и удалять прошедшие или уже начавшиеся брони.** ТЗ прямо запрещает только *создание* брони на прошедшие даты и *бронирование* прошедшего времени. Про редактирование и удаление прошлых броней ничего не сказано. Непонятно, применяется ли правило 6 к PATCH (например, можно ли сдвинуть конец брони, которая уже идёт) и разрешено ли DELETE для прошлого.
3. **Шаг времени и что такое «слот».** ТЗ говорит про «слоты», но не задаёт шаг сетки. Это может быть 30 минут (как минимальная длительность), 15 минут или произвольное время `HH:mm`. Ещё неясно, считается ли слот прошедшим, когда он уже начался или только когда закончился. Например, сейчас 10:10: доступен ли старт в 10:00?
