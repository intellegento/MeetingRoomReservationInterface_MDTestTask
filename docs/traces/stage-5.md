## Шаг 1. План

### Цель

Пользователь создаёт бронь из «Новая бронь» / «Забронировать» и правит будущую бронь кликом по ней на сетке. Форма в модальном диалоге: дата только для чтения, начало — `input type="time"`, конец — `select` из вариантов domain, название со счётчиком. Все правила — вызовы `src/domain` (`validateBooking`, варианты конца), ошибки у полей с `aria-invalid`/`aria-describedby`, сводка при отправке, защита от двойной отправки, ошибки 422 сервера у полей. Начавшиеся брони открываются только для чтения. Сегодня после 17:30 форма сообщает «На сегодня бронирование уже недоступно».

### Решения по устройству (на согласование при ревью)

1. **Слои.** `src/components/booking-form/booking-form.tsx` — презентационная форма в `Dialog` Radix (поля, ошибки, сводка, счётчик, кнопки), всё через props. `src/features/booking-form/use-booking-form.ts` — состояние формы (значения, touched, submitted, ошибки сервера, режим) и вызовы domain; `src/features/booking-form/booking-form-dialog.tsx` — связка хука, мутаций (`useCreateBooking`/`useUpdateBooking`) и компонента. `DayView` хранит, что открыто (`{ mode: "create" } | { mode: "edit", booking }`), и рендерит область `aria-live="polite"` для объявления успеха.
2. **Брони дня для проверок** берутся из того же кэша `useDayBookings(date)` — только для чтения, **значения формы** живут в `useState` формы и при перезапросе списка не меняются (Q7).
3. **Варианты конца с причиной (новая функция domain — нужно одобрение).** `getEndOptions(slot, bookings, now, editingId?)` в `src/domain/end-options.ts`: кандидаты `start + 30/60/90/120`, для каждого `{ end, available: true }` или `{ end, available: false, reason: ValidationError }` — первая ошибка `validateBooking` для этого кандидата. `getAvailableEnds` = доступные из `getEndOptions` (тесты `getAvailableEnds` не меняются). Без неё причину disabled-опции пришлось бы считать в `src/features` повтором цикла по длительностям — дубль правила B10. Опция: значение `HH:mm`, текст `HH:mm` или `HH:mm — недоступно: <сообщение domain>`, `disabled`.
4. **Пустой список стартов (новая функция domain — нужно одобрение).** `getEarliestStart(date, now): string | null` в `src/domain/day.ts`: самое раннее допустимое начало по B1, B3, B6, B12 без учёта броней — будущая дата `09:00`, сегодня `max(09:00, floor(now))`, если до 18:00 остаётся ≥ 30 мин, иначе `null`; прошедшая дата `null`. Используется (а) как подсказка-минимум: `min` у `input type="time"` и текст «Не раньше HH:mm» в `aria-describedby` (F3); (б) `null` на сегодня → диалог вместо полей показывает «На сегодня бронирование уже недоступно» и кнопку «Закрыть», запросов нет (B6, обязательный пункт plan.md). Кнопка «Новая бронь» не блокируется (решение 4 этапа 4). Брони в расчёт не входят: занятость проверяется вариантами конца (п. 3, «вариантов нет» с пояснением).
5. **Обязательность начала и конца.** Пустое поле domain отклоняет `INVALID_REQUEST` с текстом «Время должно быть в формате ЧЧ:ММ». Форма подменяет **только текст** для пустого значения: «Укажите время начала» / «Выберите время окончания» (решение о наличии значения — всё равно domain). «Сохранение блокируется до выбора конца» (F3) = отправка без конца не уходит в сеть и показывает ошибку у «Окончание»; кнопка при этом не `disabled` (иначе нет сводки ошибок).
6. **Когда видны ошибки.** Ошибка поля видна после `blur` поля (touched) или после попытки отправки. До этого `aria-invalid` нет. При отправке с ошибками — сводка `role="alert"` «Исправьте ошибки» со списком сообщений; фокус на первом невалидном поле. Ошибка без поля (`OVERLAP` клиента) — в сводке и над полями.
7. **Сброс конца.** При смене начала: если прежний конец есть среди доступных вариантов — остаётся; иначе значение `""` и подсказка «Окончание сброшено: прежнее значение не подходит к новому началу» (связана с `select` через `aria-describedby`), исчезает при выборе конца.
8. **Нет вариантов конца.** Все опции `disabled` с причиной, под `select` текст «Нет доступного окончания для этого начала» (B10, «UI поясняет, почему»).
9. **Название.** `maxLength={100}` у `input`, счётчик `N/100` по текущей длине значения (как считает `maxLength`), `aria-describedby` на счётчик. При отправке — `normalizeTitle`: создание без названия не передаёт `title`; при правке стёртое название уходит как `title: ""` (Q12). 101 символ ввести нельзя (`maxLength`), поэтому превышение проверяется ответом сервера 422 `TITLE_TOO_LONG` (`field: "title"`).
10. **Правка.** Форма предзаполнена; `editingId` передаётся в `validateBooking` и `getEndOptions` (B7). PATCH — только изменённые поля (Q12). «Сохранить» `disabled`, пока значения равны исходным (сравнение после `normalizeTitle`).
11. **Только чтение (B11, Q4).** (а) Клик по начавшейся брони открывает диалог «Бронь» только для чтения: пояснение `MESSAGES.BOOKING_LOCKED` из domain, начало и название `readOnly`, конец `disabled`, кнопок «Сохранить» нет, есть «Закрыть». **Требует изменить сетку этапа 4**: начавшаяся бронь сейчас — `div` без кнопки, тест этапа 4 «B11: … только чтение» проверяет `queryByRole("button") === null`. Предлагаю: начавшаяся бронь — кнопка «Посмотреть бронь HH:mm–HH:mm, …» с тем же пояснением, а в тесте этапа 4 проверка меняется на «нет кнопки „Изменить бронь …“, есть „Посмотреть бронь …“». **Это изменение существующего теста — нужно согласие.** (б) Бронь началась, пока форма открыта: проверка при отправке по часам клиента даёт `BOOKING_LOCKED` → запроса нет, форма переходит в только чтение. (в) Сервер ответил 422 `BOOKING_LOCKED` → то же.
12. **Отправка (U4).** Флаг «идёт отправка» в `ref` + `mutation.isPending`: второй submit до ответа игнорируется. Кнопка `disabled`, текст «Сохраняем…»; начало и название `readOnly`, конец `disabled`. Успех: диалог закрывается, фокус — на кнопку-источник (Radix), в `aria-live` «Бронь создана» / «Изменения сохранены»; список перезапрашивает хук (Q15).
13. **Ошибки сервера.** 422 с `field` → ошибка у поля (`aria-invalid`), снимается при изменении этого поля; 422 без `field` → `role="alert"` над полями. Данные формы сохраняются. 409/404/5xx/400 — этап 6 (сейчас: общее сообщение над формой без отдельной логики, тестов нет).
14. **Диалог (A2).** Radix: фокус-ловушка, Esc, возврат фокуса на кнопку-источник, `aria-labelledby` = заголовок («Новая бронь» / «Изменить бронь» / «Бронь»). Начальный фокус — поле «Начало» (`onOpenAutoFocus`), в режиме только чтения и «после 17:30» — «Закрыть».
15. **Тексты (Q17, допущения):** «Дата», «Начало», «Окончание», «Название», «Выберите окончание», «Сохранить», «Сохраняем…», «Отмена», «Закрыть», «Исправьте ошибки», «Бронь создана», «Изменения сохранены», «Посмотреть бронь …», сообщения правил — `MESSAGES` из domain.

### Отклонения от плана

1. **Брони для проверок — через props, а не `useDayBookings` в форме** (план, п. 2). Новый наблюдатель устаревшего запроса при открытии формы делал лишний `GET` (тесты 36 и 49 — `expected 3 to be 2`). Тесты не менялись.
2. **Ошибки начала при пустом конце.** `validateBooking` при пустом конце возвращает только ошибки формата, поэтому B1/B6/B12 для начала не видны. Форма вызывает `validateBooking` второй раз с концом, равным началу, и берёт из результата только ошибки не по полю `end` (`checkValues` в `use-booking-form.ts`, комментарий в коде). Решает по-прежнему domain; на согласование — допустим ли такой вызов или нужна отдельная функция domain «ошибки начала».
3. **Сброшенный конец запоминается и возвращается** (план, п. 7, найдено ручной проверкой). При вводе времени с клавиатуры начало проходит промежуточные значения: набор `13 30` даёт `13:03`, затем `13:30`. На `13:03` конец `14:00` недопустим и сбрасывался, а на `13:30` не возвращался. Теперь сброшенный конец хранится, пока не выбран другой, и возвращается, если снова допустим (подсказка сброса при этом исчезает). F3 «сбрасывается в пустое значение» соблюдается для итогового начала. **Отдельного теста на возврат нет** — предложение: `F3: конец, сброшенный промежуточным началом, возвращается, когда начало снова допускает его` (12:00/14:00 → 12:15 → 12:30: `select.value` `""` → `"14:00"`, подсказки нет).
4. **Стили диалога** написаны только после того, как ручная проверка показала диалог без CSS и под блоками сетки (`z-index` у `.booking`). В плане `globals.css` был.
5. Код ошибок `409`/`404`/`5xx`/`400` отдельно не обрабатывается: сообщение сервера над формой (`role="alert"`), данные сохраняются — полная обработка на этапе 6.

Новых `eslint-disable`, `@ts-expect-error`, `any` нет. Неочевидное: `result.errors[0]!` в `getEndOptions` — `validateBooking` с `ok: false` всегда возвращает хотя бы одну ошибку.
