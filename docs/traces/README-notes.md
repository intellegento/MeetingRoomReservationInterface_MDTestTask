## Отличия от ТЗ и ограничения

- **m-Т1. Отличия от формулировок ТЗ по решениям заказчика:** длительность кратна 30 минутам (Q2: 45 мин → 422 `DURATION_STEP`); начавшиеся брони нельзя править и удалять (Q4); прошедшие даты — только просмотр (Q13). Назвать как отличия, со ссылкой на `docs/open-questions.md`.
- **J2 (остаток после 8b). Serverless-демо:** id seed-броней одинаковы во всех инстансах (`seed-<дата>-<n>`), но изменения — нет: бронь, созданная или изменённая в одном инстансе, не видна в другом; после перезапуска состояние сбрасывается (Q9). «Чужая» бронь из `X-Mock-Force-Conflict` может не появиться при перезапросе, если он ушёл в другой инстанс — сценарий B8 на демо проверить по pre-delivery.
- **J3 — закрыт в 8c.** Пока виден список прежней даты, кнопки броней, «Новая бронь» и «Забронировать» заблокированы, для скринридера есть пояснение «Брони выбранной даты загружаются — действия недоступны».
- **m2. «Сейчас» без таймера:** клиентские часы считаются при рендере. Пока страница открыта, полоса «Прошедшее время», признак «началась» и «сегодня» после полуночи устаревают до следующего рендера. Окончательное решение — сервер (`BOOKING_LOCKED`, `START_IN_PAST`), форма их показывает (Q1).
- **m16.** Сегодня после 17:30 «Новая бронь» активна, сообщение «На сегодня бронирование уже недоступно» видно в открытом диалоге (B6 выполнено).
- **m12. Фокус во время удаления:** обе кнопки диалога `disabled` → фокус уходит на `body` до ответа сервера. У «Сохранить» не проверялось.
- **m6. HTTP-клиент не проверяет форму успешного ответа** (`parsed as T`): реальный бэкенд с другим форматом `GET` уронит экран вместо состояния ошибки U3. Для замены API (S2) — добавить проверку схемы.
- **m14.** Таймаут клиента `15_000` связан с серверной задержкой `10_000` только комментарием.
