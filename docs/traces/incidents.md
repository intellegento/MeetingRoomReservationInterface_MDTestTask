## INC-5. Мутация «показывать ошибку при AbortError» в хуке не уронила ни одного теста

- **Статус: эквивалентная мутация, не дыра** (решение заказчика, этап 4b). Тест не нужен: поведение экрана с мутацией и без неё одинаково.

- **Дата:** 2026-10-08. **Этап:** 4, мутации.
- **Что случилось:** мутация M2a — `useDayBookings` превращает `AbortError` из `BookingsApi.list` в `ApiError NETWORK` — `439 passed (439)`.
- **Причина:** мутация эквивалентна на уровне экрана. Когда у запроса даты A не остаётся наблюдателей (дата сменилась), TanStack Query сам отменяет его с `revert: true` (потому что `queryFn` читает `signal`): запрос возвращается в прежнее состояние, а поздний отказ `queryFn` — `AbortError` или подменённый `ApiError` — игнорируется. Ни при каком сценарии экрана этап 4 этот отказ не доходит до `isError`, поэтому тест его поймать не может. Защиту D2 держат: (а) чтение `signal` в `queryFn` — мутация M2c «не прокидывать signal» роняет 3 теста, включая экранный D2; (б) http-клиент пробрасывает `AbortError` — мутация M2b роняет тест этапа 3.
- **Что сделано:** тест не добавлялся (эквивалентную мутацию тест поймать не может); тесты не менялись. Мутация «показывать ошибку при AbortError» проверена в двух местах, где её можно внести (M2b, M2c) — обе пойманы.
- **Ссылки:** `docs/traces/stage-4.md` → «Мутации».

## INC-9. Ручная проверка на устройстве нашла то, что не видел встроенный браузер

- **Дата:** 2026-10-08. **Этап:** 7 (после коммита `d38f988`), 7b.
- **Что случилось:** заказчик открыл dev-сервер по IP компьютера (`<LAN-IP>`) на телефонах iOS (Safari и Chrome). Список вечно в «Загрузка…», кнопки не нажимаются. Ручная проверка этапов 4–7 во встроенном браузере шла по `localhost` и проблему не показала.
- **Причина:** Next.js 16.4.0 в dev-режиме блокирует cross-origin запросы к dev-ресурсам с хостов вне `localhost` и hostname запуска (`allowedDevOrigins`). Отклоняется WebSocket `/_next/hmr` с origin `<LAN-IP>`, и страница не гидратируется. В production этой проверки нет: сборка по IP работает. Это **ошибка процесса, не кода приложения**: ручная проверка ни разу не открывала приложение с origin, отличного от `localhost`. Чек-листы не требуют проверки на устройстве или по сетевому адресу.
- **Что сделано:** воспроизведено во встроенном браузере по `http://<LAN-IP>:3001` (сервер заказчика). Причина подтверждена логом сервера и клоном проекта с `allowedDevOrigins`. Production по IP проверен. Правка `next.config.ts` (хосты из переменной `ALLOWED_DEV_ORIGINS`, без IP в репозитории) только предложена, ждёт одобрения.
- **Предложение (одобрено и внесено в 7c):** в `docs/checklists/pre-delivery.md` добавить пункт «приложение открыто по сетевому адресу (не `localhost`) хотя бы раз — в dev с `ALLOWED_DEV_ORIGINS` и в production, — список загружается, кнопки работают».
- **Ссылки:** `docs/traces/stage-7.md`, «7b».
- **Статус (7c, коммит `ddbc94e`; отмечено в 8b по ревью m9):** **закрыт.** Правка одобрена и внесена: `next.config.ts` берёт хосты из `ALLOWED_DEV_ORIGINS`, скрипт `dev:lan`, переменная в `.env.example`, два пункта в `pre-delivery.md` (dev и production по сетевому адресу).
