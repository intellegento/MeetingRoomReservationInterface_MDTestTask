## Этап 1. Каркас + domain — 50 мин

**Цель.** Рабочий каркас Next.js + TypeScript strict с одной командой `npm run gate`. Слой `src/domain` содержит все бизнес-правила в виде чистых функций.

**ID требований.** B1, B2, B3, B4, B5, B6, B7, B9, B10, B11, B12 (уровень unit), S1 (правила вне React), S3.

**Порядок внутри этапа.**
1. Каркас: Next.js, TS strict, ESLint с правилами границ слоёв и запретом `Date.now()` / `new Date()` без аргументов в `src/domain`, тест-раннер. Все зависимости записываются в журнал `architecture.md` до установки.
2. `npm run gate` работает на пустом наборе тестов.
3. Тесты domain → красный прогон → **СТОП** → реализация.

**Тесты, которые пишутся первыми** (unit, `src/domain`):
- разбор и проверка формата `HH:mm` и `YYYY-MM-DD`, сравнение времени в минутах (T5);
- граничные значения B1–B4, B10 из критериев приёмки;
- пересечения B5: все 8 случаев и касание границ (T3);
- исключение собственной брони B7 (T4);
- «сейчас» в поясе комнаты B9: момент `2026-10-07T19:30Z` даёт «сегодня» `2026-10-08`, результат не зависит от `TZ` процесса (T1);
- прошедшее время B6 и точность до минуты B12: `10:10:00`, `10:10:59`, `10:11:00`;
- «начавшаяся бронь» B11;
- варианты конца для `select` (B10): ограничение 18:00 и следующей бронью, собственная бронь при редактировании не мешает;
- порядок проверок (B4 и B10 для 121 мин).

**Definition of Done.**
- `npm run gate` зелёный: типы, lint, тесты, сборка.
- Каждый граничный пример B1–B7 и B9–B12 из requirements покрыт тестом с ID в названии.
- В `src/domain` нет React, `fetch`, `Date.now()`, `new Date()` без аргумента. Lint это ловит. Проверка: временно вставить запрещённый вызов, убедиться, что lint падает, откатить.
- Журнал зависимостей заполнен.
- Ручные мутации для B5, B7, B9, B10, B12 из testing.md выполнены, каждая уронила хотя бы один тест.
- `npm run gate` включает все шаги из testing.md (правило 7): ESLint-правила и `policy-check` из раздела «Автоматические проверки правил AGENTS.md», повторный прогон с `TZ=America/Los_Angeles`. Git-хук `pre-commit` запускает gate. Каждая проверка подтверждена намеренным нарушением.

**Что обязательно в трейсе.** Вывод красного прогона. Вывод зелёного gate. Таблица «мутация → упавший тест». Проверка lint-правил на запрещённых вызовах. Список зависимостей со ссылкой на журнал. Окончательный состав `npm run gate`.

## Этап 2. Mock API — 30 мин

**Цель.** Сервер на Route Handlers проверяет все правила через `src/domain`, хранит данные в памяти на `globalThis` с seed и отвечает в едином формате ошибок.

**ID требований.** B1–B7, B10–B12 (уровень api), B8 (серверная часть `X-Mock-Force-Conflict`), B9 (главные часы — серверные), F2 (seed), F4, F5, F6 (уровень api), U4 (`X-Mock-Delay`).

**Тесты, которые пишутся первыми** (api: обработчики вызываются с `Request` и фиксированными часами):
- `GET ?date=` — фильтр по дате, сортировка, seed на сегодня и завтра от «сегодня» по Бишкеку;
- `400` на битый формат и неизвестные поля, `422` с `code`/`field` на каждое бизнес-правило, `409` с `conflictWith`, `404` на несуществующий `id`;
- `PATCH` частичный: склейка, `title:""` стирает название, смена `date` (один тест, Q5), повторная проверка всех правил;
- `PATCH` и `DELETE` начавшейся брони → 422 (B11);
- `DELETE` → 204, повторный → 404;
- каждое правило проверяется прямым HTTP-запросом, без UI (T10);
- dev-заголовки: с `ENABLE_DEV_TOOLS` `X-Mock-Force-Conflict: 1` → 409 и «чужая» бронь в store. Без флага → заголовки игнорируются (201). `X-Mock-Delay` задерживает ответ.

**Definition of Done.** Gate зелёный. Route-файлы — тонкие обёртки над `src/server`. Выполнена мутация «удалить серверную проверку прошедшего времени», тест упал.

**Что обязательно в трейсе.** Красный и зелёный прогоны. Таблица «метод + случай → статус → `code`». Результат мутации. Ручной запрос `curl` к запущенному dev-серверу: один успешный и один 409.

## Этап 3. API-клиент и хуки — 20 мин

**Цель.** UI работает с сервером только через интерфейс `BookingsApi` и хуки `src/features`. Ошибки приходят в UI как типизированная `ApiError`.

**ID требований.** S1, S2, U3 (разбор ошибок), F1 (смена даты без гонок), F4–F6 (перезапрос после мутаций, Q15).

**Тесты, которые пишутся первыми:**
- клиент: разбор `{ error: { code, message, field?, details?, conflictWith? } }` для 400/404/409/422. Тело не в формате или сетевая ошибка → общая ошибка;
- хук списка: быстрая смена даты A → B, поздний ответ A игнорируется (T9);
- мутации: после успешных `POST`/`PATCH`/`DELETE` ровно один перезапрос списка, оптимистичных изменений нет;
- S2: хук списка работает с тестовой in-memory реализацией `BookingsApi` без HTTP;
- dev-флаги клиента добавляют заголовки `X-Mock-*` только при включённой dev-панели.

**Definition of Done.** Gate зелёный. Lint запрещает импорт `src/api` из `src/components`. Проверено намеренным нарушением. Хуки получают `BookingsApi` через параметр или контекст, их тесты работают на тестовой in-memory реализации (S2). Если для состояния нужна библиотека, она записана в журнал зависимостей с обоснованием.

**Что обязательно в трейсе.** Красный и зелёный прогоны. Сигнатура `BookingsApi`. Проверка lint-границы. Короткое описание, как заменить mock на реальный API (заготовка для README).

## Этап 4. Просмотр дня — 40 мин

**Цель.** Пользователь выбирает дату и видит брони дня во всех состояниях. Прошедшие даты и начавшиеся брони только для чтения.

**ID требований.** F1, F2, U1, U2, U3 (ошибка загрузки), B6 (UI: прошедшая дата), B9 (UI: «сегодня» по Бишкеку), B11 (UI: только чтение), B12 (UI).

**Тесты, которые пишутся первыми** (ui):
- при открытии выбрана сегодняшняя дата по Бишкеку, браузер в другом поясе;
- U1: `role="status"` и `aria-busy` во время загрузки;
- U2: «На эту дату броней нет»;
- U3: ошибка загрузки → «Повторить» → повторный запрос;
- F2: сортировка по старту, «Без названия»;
- прошедшая дата: нет активного «Создать», есть пояснение;
- начавшаяся бронь: нет активных «Изменить» и «Удалить», есть пояснение;
- линия «сейчас» на сегодняшней дате (срезаемо, см. «Порядок среза»).

**Definition of Done.** Gate зелёный. Экран работает в `npm run dev` на seed-данных.

**Что обязательно в трейсе.** Красный и зелёный прогоны. Скриншоты или описание ручной проверки состояний (загрузка, пусто, ошибка, прошлая дата, сегодня). Формат представления дня и почему выбран он.

## Этап 5. Форма — 50 мин

**Цель.** Создание и редактирование брони. Форма валидирует данные через domain, показывает ошибки у полей, не допускает двойной отправки. Её состояние не зависит от списка.

**ID требований.** F3, F4, F5, B6, B7, B10, B12 (UI), U3 (422 у поля), U4.

**Тесты, которые пишутся первыми** (ui):
- начало — `input type="time"`, на сегодня есть подсказка-минимум. Конец — `select` с вариантами по B10, включая ограничение следующей бронью и случай «вариантов нет»;
- при редактировании собственная бронь не ограничивает конец (T4). Дату изменить нельзя;
- клиентская валидация не пускает запрос с нарушением правил;
- 422 с `field` → ошибка у поля, `aria-invalid`, `aria-describedby`, данные сохранены;
- отказ сервера на границе минуты (B12) → ошибка у начала, данные сохранены;
- `title`: обрезка пробелов, счётчик `N/100`, 101 символ → ошибка;
- **обязательно (решение заказчика, этап 4):** сегодня после 17:30 (до 18:00 меньше 30 мин, свободных стартов нет) — сообщение «На сегодня бронирование уже недоступно» (B6); поведение формы, когда список допустимых стартов пуст (кнопка «Новая бронь» на этапе 4 после 17:30 не блокируется — решение 4, `docs/traces/stage-4.md`);
- U4: «Сохранение…», `disabled`, два клика → один `POST` (T8);
- успешное создание → перезапрос и бронь в списке.

**Definition of Done.** Gate зелёный. Мутация «убрать `disabled` у кнопки во время отправки» уронила тест. Создание и правка проверены вручную в `npm run dev`.

**Что обязательно в трейсе.** Красный и зелёный прогоны. Результат мутации. Ручная проверка создания и правки.

## Этап 6. Удаление, 409, ошибки — 40 мин

**Цель.** Удаление с подтверждением. Полная обработка конфликта 409 по Q7. Обработка 404/500/сетевых ошибок. Dev-панель для демо.

**ID требований.** F6, B8, B11 (удаление), U3 (мутации), U4 («Медленная сеть»).

**Тесты, которые пишутся первыми** (ui):
- удаление: подтверждение → `DELETE` → перезапрос. Ошибка `DELETE` → бронь остаётся, сообщение;
- 409 при создании и при правке: сообщение `role="alert"`; данные формы, включая **изменённые** значения, на месте (T6); поля времени помечены и пометка снимается после правки; ровно один перезапрос на дату **из формы** (T7);
- 404 при правке → «Бронь была удалена», данные сохранены, можно сохранить как новую;
- 500 или сетевая ошибка при сохранении → сообщение, данные сохранены, можно повторить;
- dev-панель: есть в DOM только при `NEXT_PUBLIC_ENABLE_DEV_TOOLS`, переключатели добавляют заголовки.

**Definition of Done.** Gate зелёный. Мутации «не перезапрашивать список после 409» и «сбрасывать форму после ошибки» уронили тесты. 409 воспроизведён вручную через dev-панель.

**Что обязательно в трейсе.** Красный и зелёный прогоны. Результаты мутаций. Ручной сценарий 409 по шагам с итогом.

## Порядок среза

Применяется по очереди, начиная с первого пункта, и только по решению заказчика:

1. **`jest-axe`** — убрать автоматическую проверку a11y. Остаются ручные проверки и тесты ролей и имён (этап 7).
2. **Линия «сейчас»** в представлении дня (этап 4).
3. **Ревьюер сокращается до pre-delivery.** Вместо независимого ревью только прохождение чек-листа [pre-delivery.md](checklists/pre-delivery.md) (этап 8).
4. **Dev-панель 409 заменяется инструкцией с `curl`.** В README — команды, которыми занять слот в обход UI и получить 409. Серверные заголовки `X-Mock-*` остаются (этап 6).

## Не срезается

- **B1–B8**: бизнес-правила, проверка на сервере и обработка 409 в UI.
- **U1–U4**: загрузка, пустое состояние, ошибка, отправка формы.
- **Разделение API и UI** (S1, S2).
- **README с фактическим временем** (D2, по `docs/time-log.md`).
