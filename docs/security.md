# Безопасность

## Что агенту недоступно
- **`.env*`** (кроме `.env.example`): агент не читает, не создаёт и не меняет. В `.env.example` — только имена переменных и плейсхолдеры.
- **`~/.ssh`**: агент не читает и не меняет.
- **`gh auth token`** и любые способы вывести токен: агент не запускает. Агент не просит токены, пароли и ключи и не записывает их ни в код, ни в docs, ни в чат.

## Секреты проекту не нужны
Реального бэкенда, БД, авторизации и интеграций нет (ТЗ). Переменные окружения проекта — только несекретные флаги:
- `NEXT_PUBLIC_ENABLE_DEV_TOOLS` — показывать dev-панель (Q8);
- `ENABLE_DEV_TOOLS` — сервер учитывает dev-заголовки `X-Mock-*` (Q8).

Если по ходу работы кажется, что нужен секрет, — это вопрос заказчику, а не повод его завести.

## Доступ к GitHub
- Для задания используется **отдельный SSH-ключ с passphrase**, созданный только для этого репозитория/аккаунта.
- Авторизацию (`gh auth login`, разблокировку ключа в `ssh-agent`) выполняет **человек в отдельном терминале**. Агент только пользуется уже открытой сессией (`git push`, `gh repo ...`).
- Если push или `gh` требуют авторизации, агент останавливается и говорит, что нужно сделать человеку. Обходить нельзя.

## Деплой
Деплой (Vercel и т.п.), подключение репозитория, переменные окружения на хостинге и любые токены — **на стороне человека**. Агент готовит код, README и инструкцию: какие флаги включить на демо.

## Переписка с AI
Перед коммитом каждого файла в `docs/traces/chats/` его проверяют на секреты: токены (`gho_`, `ghp_`, `github_pat_`, `sk-`, `xox`), приватные ключи (`BEGIN ... PRIVATE KEY`), пароли и строки вида `token=`, `secret=`, `password=`. Найденное маскируется до коммита.

## После сдачи (делает человек)
1. `gh auth logout`.
2. Удалить SSH-ключ задания в GitHub (Settings → SSH and GPG keys).
3. Удалить этот ключ локально и убрать его из `ssh-agent`.
