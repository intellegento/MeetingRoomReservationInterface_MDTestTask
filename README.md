# Meeting Room Reservation Interface

Интерфейс бронирования одной переговорной комнаты: просмотр броней на дату, создание, правка и удаление брони.
Рабочий день 09:00–18:00 в поясе комнаты `Asia/Bishkek`. Тестовое задание — ТЗ: [docs/tz.md](docs/tz.md).
Таймбокс 4–6 ч, приоритет — инженерная аккуратность, а не дизайн.

**Демо:** https://meeting-room-reservation-interface.vercel.app/ (dev-панель включена, см. «Как воспроизвести 409»).

**Переписка с AI:** [docs/traces/chats/](docs/traces/chats/) — по файлу на этап, `Stage N - <тема>.md`.

## 1. Как запустить

Нужен Node.js 22.13 или новее (`engines` в `package.json`). Секреты и `.env` не нужны: все переменные необязательны
(таблица — в разделе «Деплой»).

| Команда | Что делает |
|---------|------------|
| `npm ci` | установка зависимостей; скрипт `prepare` подключает git-хуки из `.githooks` |
| `npm run dev` | dev-сервер, http://localhost:3000 |
| `NEXT_PUBLIC_ENABLE_DEV_TOOLS=true ENABLE_DEV_TOOLS=true npm run dev` | то же с dev-панелью (409, «Медленная сеть») |
| `ALLOWED_DEV_ORIGINS="$(ipconfig getifaddr en0)" npm run dev:lan` | dev-сервер для телефона в той же сети: `http://<IP>:3000` (macOS; на Linux — `hostname -I`). Без `ALLOWED_DEV_ORIGINS` Next в dev не отдаёт свои ресурсы чужому хосту и страница не оживает (INC-9). Только точные хосты через запятую, без `*` |
| `npm test` | все тесты (Vitest) в `TZ=UTC` |
| `npm run test:tz` | тесты `src/domain` и `*.tz.test.*` в `TZ=America/Los_Angeles` |
| `npm run gate` | полная проверка: `tsc --noEmit`, `eslint --max-warnings 0`, `policy-check`, тесты в двух поясах, `next build`. Последний прогон: 568 тестов (UTC) и 250 (Los Angeles), всё зелёное |
| `npm run build` / `npm start` | production-сборка и запуск |

Хук `pre-commit` запускает `policy-check --staged` и весь gate — коммит при красном gate невозможен.

## 3. Архитектура

| Слой | Что внутри |
|------|------------|
| `src/domain` | типы, константы, чистые функции: время в минутах, валидация B1–B7 и B10–B12, пересечения, варианты конца, «сейчас» в поясе комнаты (B9), коды и тексты ошибок. Без React, `fetch`, ввода-вывода и без `Date.now()` / `new Date()` без аргумента |
| `src/server` | mock API: обработчики, in-memory store на `globalThis`, seed, разбор запроса (400), ошибки домена → 422/409/404, dev-заголовки `X-Mock-*` |
| `src/api` | интерфейс `BookingsApi`, HTTP-реализация, разбор `{ error: {...} }` в типизированную `ApiError`, таймаут, отмена |
| `src/features` | хуки сценариев: список по дате, форма (своё состояние, независимое от списка — Q7), мутации и перезапрос, обработка 409/422/404, dev-панель |
| `src/components` | презентационные компоненты: данные и колбэки только через props |
| `src/app` | страница и тонкие `route.ts` над `src/server` |

```
            src/app (страницы)          src/app/api/** (route.ts)
              │        │                        │
              ▼        ▼                        ▼
       src/features ─► src/components       src/server
          │    │            │                   │
          ▼    └──────┐     │                   │
       src/api        ▼     ▼                   │
          │       src/domain ◄──────────────────┘
          └──────────►▲
```

- Одни и те же функции `src/domain` дают подсказки в UI и окончательный вердикт на сервере (Q1).
- `src/api` и `src/server` не знают друг о друге: общий контракт — HTTP и типы из `src/domain`.
- `Date.now()` / `new Date()` без аргумента — только в двух файлах-часах: `src/server/clock.ts` (главные часы) и `src/features/clock.ts` (подсказки).
- Границы проверяет ESLint в gate. Полная таблица разрешённых импортов — [docs/architecture.md](docs/architecture.md).

### Как заменить mock на реальный API

1. **Бэкенд с тем же HTTP-контрактом** (`GET /bookings?date=`, `POST /bookings`, `PATCH /bookings/:id`, `DELETE /bookings/:id`,
   тело ошибки `{ error: { code, message, field?, details?, conflictWith? } }`, 400/404/409/422): задать
   `NEXT_PUBLIC_API_URL=https://…` и пересобрать. Код UI и хуков не меняется.
2. **Другой транспорт или формат:** написать свою реализацию интерфейса `BookingsApi` (`src/api/bookings-api.ts`: `list`, `create`,
   `update`, `remove`) и передать её в `BookingsApiProvider` в `src/features/app-providers.tsx`. Хуки и компоненты
   знают только интерфейс — ui-тесты так и работают, с `FakeBookingsApi`.

Что учесть: HTTP-клиент не проверяет форму **успешного** ответа (`parsed as T`). Бэкенд с другим форматом `GET` уронит экран
вместо состояния ошибки — для реального API стоит добавить проверку схемы (ревью, m6). Таймаут клиента 15 с связан с
предельной задержкой mock 10 с только комментарием (m14).

## 5. Решения и допущения заказчика

Спорные места ТЗ были вынесены вопросами Q1–Q25 и решены заказчиком до кода. Полный текст — [docs/open-questions.md](docs/open-questions.md#решения). Главное:

| Решение | Что значит |
|---------|------------|
| Q1. Пояс комнаты | `ROOM_TIMEZONE=Asia/Bishkek` (UTC+6) на клиенте и сервере, «сейчас» — одна функция. Часы сервера главные; клиентские — только для подсказок. Отказ сервера из-за расхождения часов — обычная ошибка валидации без потери данных формы |
| Q2. Кратность 30 минутам, старт любой минуты | длительность 30/60/90/120, сервер отвечает `DURATION_STEP`. Начало — `input type="time"`, конец — `select` из `start + 30/60/90/120`, ограниченный 18:00 и следующей бронью. **Строже ТЗ:** 45 минут ТЗ разрешает, здесь — 422 |
| Q3. Точность до минуты | слот прошёл, если `start < floor(now, минута)` |
| Q4. Начавшиеся брони | нельзя ни править, ни удалять. **Шире ТЗ:** ТЗ запрещает только бронировать прошедшее время |
| Q5. Дата не меняется в UI | при правке поле даты недоступно. API `PATCH` принимает `date` и проверяет результат |
| Q6. Название | необязательно, `trim`, максимум 100 символов, превышение → 422 и счётчик у поля |
| Q7. Форма и список независимы | при 409 поля времени помечаются и остаются редактируемыми; бронь удалена → «Бронь была удалена» и «Сохранить как новую бронь» |
| Q8. Dev-панель | см. раздел 6 |
| Q9. In-memory store | см. раздел 7 и «Деплой» |
| Q10 | любой день недели, выходных и праздников нет |
| Q11. Коды | 400 — формат, 422 — бизнес-правило, 409 — только пересечение, единое тело ошибки |
| Q12 | `PATCH` частичный, `title: ""` стирает название |
| Q13. Прошедшие даты | только просмотр. **Шире ТЗ** (там — «создание недоступно») |
| Q14 | горизонта бронирования вперёд нет |
| Q15 | после `POST`/`PATCH`/`DELETE` список перезапрашивается, без оптимистичных обновлений |
| Q16 | seed — брони на сегодня и завтра от «сегодня» в поясе комнаты |
| Q17 | интерфейс на русском |
| Q19–Q25 | `DATE_IN_PAST` / `START_IN_PAST`; порядок ошибок 404 → 400 → 422 → 409; поведение dev-конфликта при `PATCH`; `ENABLE_DEV_TOOLS` — только строка `true`; предел `X-Mock-Delay` 10 000 мс |

Допущения реализации (записаны в трейсах этапа 4):

- **`retry: 1` для загрузки списка** (`src/features/app-providers.tsx`). По умолчанию TanStack Query повторяет 3 раза с паузами,
  и ошибка «Не удалось загрузить брони» появлялась бы примерно через 7 с. Один повтор сглаживает разовый сбой, ошибка видна
  примерно через 1 с, дальше — кнопка «Повторить».
- **Seed только на сегодня и завтра.** Создать бронь на прошедшую дату нельзя, поэтому прошедшие даты всегда пустые.
  Брони «только чтение» вручную видны на сегодняшних начавшихся бронях; на прошедшей дате их проверяет ui-тест.

## 6. Как воспроизвести 409 и другие ошибки

**Dev-панель** включается двумя флагами: `NEXT_PUBLIC_ENABLE_DEV_TOOLS=true` (клиент, встраивается при сборке) и
`ENABLE_DEV_TOOLS=true` (сервер). Оба — только строкой `true`. На демо оба включены. Панель «Инструменты разработчика» —
внизу экрана, в ней два переключателя:

- **«Симулировать конфликт при следующем сохранении»** — клиент отправляет `X-Mock-Force-Conflict: 1`. Сервер кладёт в store
  «чужую» бронь на запрошенный интервал и отвечает 409 с `conflictWith`. В форме: сообщение, поля времени помечены,
  данные на месте, список перезапрошен. **Срабатывает один раз:** переключатель снимается после ближайшего сохранения.
  Исключение (Q25): при `PATCH`, где новый интервал пересекает старый интервал этой же брони, «чужая» бронь в store
  не кладётся, `conflictWith` — бронь с новым id, которой нет в списке.
- **«Медленная сеть»** — `X-Mock-Delay: 2000` для сохранения и удаления: видно «Сохраняем…», двойной клик не создаёт двух броней.
  **На загрузку списка не влияет:** `BookingsApi.list` не принимает заголовки.

**Через curl** (нужен `ENABLE_DEV_TOOLS=true` на сервере; `B=http://localhost:3000/api/bookings` или адрес демо):

| Ошибка | Запрос |
|--------|--------|
| 409 пересечение | `POST` того же интервала дважды или `POST` с `-H 'X-Mock-Force-Conflict: 1'` |
| 422 бизнес-правило | `POST` `{"date":"<завтра>","start":"08:30","end":"09:30"}` → `OUTSIDE_WORKING_HOURS` |
| 404 | `DELETE $B/<несуществующий id>` |
| 400 формат | неизвестное поле или битое время в теле |
| задержка | `-H 'X-Mock-Delay: 3000'` (до 10 000 мс) |

Пример: `curl -X POST "$B" -H 'Content-Type: application/json' -H 'X-Mock-Force-Conflict: 1' -d '{"date":"<завтра>","start":"14:00","end":"15:00"}'`

Без серверного флага заголовки `X-Mock-*` игнорируются. Ошибку загрузки списка (U3, «Повторить») через панель не вызвать.
Её проверяют ui-тесты; вручную на этапе 4 её получали отказом `/api/bookings` в браузере.

**404 при удалении — мягкий успех:** «Бронь уже удалена», список перезапрашивается. При правке 404 → «Бронь была удалена»
и «Сохранить как новую бронь».

## 7. Ограничения демо

- **In-memory store на serverless (Q9).** Брони живут в памяти процесса. Состояние сбрасывается при холодном старте и новом
  деплое, а у разных инстансов память разная: бронь, созданная в одном, может быть не видна в другом.
- **Seed детерминирован (J2, этап 8b).** Каждый инстанс создаёт одни и те же seed-брони с id `seed-<сегодня>-<n>`, поэтому
  правка и удаление seed-броней не упираются в расхождение id.
- **Smoke-проверка демо (9b)** через curl прошла 6 из 6 шагов (200, 201 → 409, 409 по `X-Mock-Force-Conflict`, 204, 422, 404),
  все запросы видели одно состояние. Это **не доказывает**, что инстанс один: заголовок `x-vercel-id` — id запроса,
  а не инстанса. Расхождение инстансов не подтверждено и не опровергнуто. Поэтому «чужая» бронь после симуляции
  конфликта теоретически может не появиться в списке, если перезапрос уйдёт в другой инстанс.
- Подробно о переменных и Vercel — раздел «Деплой».

## Деплой

Проект собирается и запускается на Vercel без настроек: Framework Preset — Next.js, команды по умолчанию
(`npm ci`, `next build`), Node.js 22.13 или новее (`engines` в `package.json`). Секретов, токенов и внешних
сервисов нет: mock API работает внутри того же приложения (`/api/bookings`).

### Переменные окружения

Все переменные необязательны и несекретны. Без них приложение работает как обычный интерфейс без dev-инструментов.
Флаги включает только строка `true`, любое другое значение — выключено.

| Переменная | Где читается | По умолчанию | На демо |
|------------|--------------|--------------|---------|
| `NEXT_PUBLIC_ENABLE_DEV_TOOLS` | клиент, **встраивается при сборке** | выключено: dev-панели нет | `true`, если нужна демонстрация конфликта (B8) и медленной сети |
| `ENABLE_DEV_TOOLS` | сервер, на каждый запрос | выключено: заголовки `X-Mock-*` игнорируются | `true` вместе с предыдущей |
| `DISABLE_MOCK_DELAY` | сервер | задержка ответа 300–800 мс (видно состояние загрузки) | не задавать |
| `NEXT_PUBLIC_API_URL` | клиент, встраивается при сборке | `/api` (встроенный mock) | не задавать; нужна при замене mock на реальный API |
| `ALLOWED_DEV_ORIGINS` | только `next dev` | пусто | не нужна |

**Что видит проверяющий:**

- Оба флага `true` — внизу экрана блок «Инструменты разработчика» с переключателями «Симулировать конфликт
  при следующем сохранении» (сервер ответит 409 с «чужой» бронью) и «Медленная сеть» (задержка 2 с,
  видно «Сохраняем…»). Без этого конфликт (B8) можно увидеть только двумя вкладками, а на serverless — ненадёжно (см. ниже).
- Оба выключены — dev-панели нет, сервер не реагирует на `X-Mock-*`.
- Включён только `NEXT_PUBLIC_ENABLE_DEV_TOOLS` — панель видна, но переключатели ничего не делают. Так не настраивать.

Переменные задаются в Vercel: Project → Settings → Environment Variables. `NEXT_PUBLIC_*` встраивается в клиентский
код при сборке, поэтому после изменения любой переменной нужен новый деплой (Deployments → Redeploy).

Флаги на демо открывают заголовки `X-Mock-*` любому посетителю. Это допустимо: данные — только in-memory mock,
задержка ограничена 10 с.

### Ограничение: in-memory store на serverless

Брони хранятся в памяти процесса (Q9). На Vercel API работает в serverless-функциях, и у каждого инстанса своя память:

- состояние сбрасывается при холодном старте и новом деплое — созданные, изменённые и удалённые брони пропадают;
- если запросы попадают в разные инстансы, бронь, созданная или изменённая в одном, не видна в другом;
- seed детерминирован (после J2): каждый инстанс при первом обращении создаёт одни и те же брони с одинаковыми
  id `seed-<дата>-<n>` от «сегодня» по поясу `Asia/Bishkek`, поэтому правка и удаление seed-броней не дают
  ложного «Бронь уже удалена» из-за расхождения id;
- «чужая» бронь из «Симулировать конфликт» может не появиться в списке после перезапроса, если он ушёл в другой
  инстанс. Сообщение о конфликте и сохранённые данные формы видны всегда.

Для постоянного хранения нужен реальный бэкенд: mock заменяется через `NEXT_PUBLIC_API_URL` и интерфейс `BookingsApi`.

## 9. Как я работал с агентом

Код, тесты и документы писал AI-агент (Claude Code) по командам заказчика, поэтапно. Заказчик принимал каждый этап.

**Файлы контекста.** [AGENTS.md](AGENTS.md) (подключён из `CLAUDE.md`) — правила: порядок этапа, запреты, запись времени.
`docs/`: ТЗ (не редактируется), [requirements.md](docs/requirements.md) с ID и критериями приёмки,
[open-questions.md](docs/open-questions.md) с решениями заказчика, [architecture.md](docs/architecture.md), [plan.md](docs/plan.md)
(этапы, таймбоксы, Definition of Done), [testing.md](docs/testing.md), [security.md](docs/security.md), чек-листы `stage-gate` и `pre-delivery`.
Запреты на `.env*`, `~/.ssh` и `gh auth token` продублированы deny-правилами в `.claude/settings.json`.

**Цикл этапа.** `date` в time-log → в трейсе цитата команды и план (цель, ID, файлы, тесты) → красные тесты, показ
красного прогона, **стоп** → реализация → `npm run gate` → доказательства в трейсе и stage-gate → `date` → коммит
`stage N: … (gate green)` и push → **стоп** до следующей команды. Ожидание в тесте выводится из правила или контракта,
а не из реализации. Старые тесты меняются только с согласия заказчика, и перед изменением поведения агент ищет
через `grep` все тесты, которые его проверяют.

**Мутации.** После каждого этапа агент вручную ломал код (например, `<` вместо `<=` в B11, убранный перезапрос после 409,
флаг из любой строки вместо `"true"`) и проверял, что тесты падают. Не пойманная мутация — дыра: дописывался тест или,
по решению заказчика, мутация признавалась эквивалентной (INC-5, INC-7).

**Независимое ревью (этап 8).** Отдельный проход «ревьюером»: трассировка ID → код → тест, сверка с ТЗ, 8 выборочных мутаций
(все пойманы), процесс и секреты. Итог: 3 blocker (сдача), 3 major, 17 minor. Major исправлены в 8b и 8c через красные тесты:
детерминированный seed (J2), блокировка действий при загрузке даты (J3), инцидент J1 → INC-10.

**Трейсы:** [docs/traces/INDEX.md](docs/traces/INDEX.md) — навигация по этапам, коммитам и трейсам.

**Переписка с агентом:** [docs/traces/chats/](docs/traces/chats/) — по файлу на этап 0–9 (`Stage N - <тема>.md`): команды
заказчика и ответы агента, скопированные из интерфейса чата; вывод команд в них свёрнут.
